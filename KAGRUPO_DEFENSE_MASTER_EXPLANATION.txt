MGA PANGUNAHING GINAWA MO SA BACKEND:
1. RESTful Routing sa routes/web.php:
   - Hinati namin sa dalawang major portals:
     * Student Storefront View: GET /
     * Dedicated Admin Console: GET /admin
   - REST API Endpoints para sa Real-Time Ajax:
     * GET /api/realtime/sync - nagse-serve ng live inventory, ticket messages,
       at activity logs bawat 2 segundo.
     * POST /api/reservations - pag-create ng order na may automatic reference
       code generation (format: ICS-2026-XXXXX).
     * PATCH /api/reservations/{id}/status - pag-update ng order status
       (Pending, Ready for Pickup, Claimed, Cancelled).
     * POST /api/products, POST /api/products/{id}, DELETE /api/products/{id} -
       kumpletong CRUD operations para sa mga merchandise items.
     * POST /admin/logout at /oauth/logout - secure session clearing at audit logging.

2. Enterprise-Grade Authentication (OnePass OAuth 2.0 + OIDC PKCE):
   - Sa OAuthController.php, nag-integrate kami ng Single Sign-On (SSO) gamit ang
     RFC 7636 PKCE (Proof Key for Code Exchange) S256 method.
   - Walang plain-text password na dumadaan sa server. Ang identity token ay
     nagse-share ng verified student claims: name, student_id, college email,
     course/department, year level, section, at avatar photo.
   - Naglagay din kami ng Local Student Portal fallback (StudentAuthController.php)
     para sa offline development o mabilisang demonstration sa defense.

3. Inventory Business Logic & Race Condition Guard:
   - Sa MerchController.php, may matibay na stock validation rules:
     * Bago mag-reserve ang student, chine-check kung available pa ang stock
       sa napiling size (XS, S, M, L, XL, etc.).
     * Kapag nag-reserve, nag-i-increment ang `units_reserved` at nagde-decrement
       ang `current_stock`.
     * Kapag na-cancel ang order, automatic na ibinabalik ang stock sa inventory
       gamit ang atomic database operations para maiwasan ang overselling.

MGA PANGUNAHING GINAWA MO SA DATABASE:
1. Relational Schema Architecture (16 Tables kabuuan):
   - Pangunahing Tables ng System:
     * `products`: naglalaman ng `item_code` (UNIQUE), `name`, `price`, `initial_stock`,
       `current_stock`, `units_sold`, `units_reserved`, at JSON column para sa `sizes`.
     * `reservations`: may `ref_code` (UNIQUE), student details, `items` (JSON array),
       `total_amount`, `pickup_date`, `pickup_slot`, payment details, at `status`.
     * `students`: naka-store ang verified campus identity tulad ng `student_id` (UNIQUE),
       `name`, `email` (UNIQUE), `department`, `section`, `year_level`, at `avatar`.
     * `system_users`: mga authorized administrative officers na may role hierarchy
       (Admin, Officer).
     * `support_tickets` at `support_ticket_messages`: 1-to-many relationship para sa
       customer helpdesk at live chat logs.
     * `activity_logs`: kumpletong audit trail table (user_code, user_name, action,
       activity description, module, client ip_address, timestamps).

2. Cloud Migration sa TiDB Cloud (AWS Singapore):
   - Sa halip na iwan ang database sa localhost XAMPP, inilipat natin ito sa
     TiDB Serverless Cloud Database (`gateway01.ap-southeast-1.prod.aws.tidbcloud.com:4000`).
   - Naka-enable ang secure SSL connection gamit ang `PDO::MYSQL_ATTR_SSL_CA => true`
     at `PDO::MYSQL_ATTR_SSL_VERIFY_SERVER_CERT => false` sa config/database.php.
   - Dahil dito, 24/7 accessible ang database mula sa kahit saang lupalop ng mundo
     at naka-sync ang live website sa Render sa parehong cloud database.

3. Pag-maintain ng Data Integrity at ACID Compliance:
   - Gumamit kami ng Unique Constraints sa `email`, `student_id`, at `ref_code`
     upang maiwasan ang duplicate records.
   - Parameterized queries ang lahat ng execution sa pamamagitan ng Laravel Eloquent ORM,
     kayang-kayang humarang sa anumang uri ng SQL Injection attacks.

TOP 3 QUESTIONS NA PWEDENG ITANONG SA DATABASE AT SAGOT MO:
Q1: "Bakit TiDB Cloud ang pinili niyo imbes na traditional local MySQL sa XAMPP?"
A1: "Kasi po ang TiDB Serverless Cloud ay MySQL-compatible distributed cloud database
na naka-host sa AWS Singapore. Dahil naka-deploy ang aming system sa internet sa
Render.com, kailangan po ng cloud database na may mataas na availability at
hindi naka-depende sa local laptop ng estudyante."

Q2: "Bakit JSON data type ang ginamit ninyo sa sizes ng products at items ng reservations?"
A2: "Ang JSON column po sa MySQL/TiDB ay nagbibigay ng flexibility para makapag-imbak
ng dynamic key-value pairs (tulad ng quantity per size: XS:10, S:25, M:40) nang hindi
nangangailangan ng hiwalay na napakaraming pivot tables, na nagpapabilis sa query
performance ng catalog."

Q3: "Paano niyo na-handle ang unique constraints kapag nag-sign in ang user mula sa OAuth?"
A3: "Dahil parehong may UNIQUE constraint ang `student_id` at `email` sa `students` table,
hindi po kami basta nag-i-insert. Gumawa po kami ng smart lookup gamit ang
`where('email', $email)->orWhere('student_id', $studentId)` bago mag-update o mag-insert
upang 100% maiwasan ang SQL Integrity constraint violation."

--------------------------------------------------------------------------------
CHALLENGE 1: ANG DOCKER 500 SERVER ERROR SA RENDER DEPLOYMENT
--------------------------------------------------------------------------------
• Ano ang naging problema?
  Nang una nating i-deploy ang Laravel application sa Render.com, nagpakita ang
  browser ng '500 Server Error'.
• Bakit nag-error?
  1. Default ng Apache na ituro ang DocumentRoot sa `/var/www/html/` sa halip na
     sa `/var/www/html/public`, kaya hindi nahanap ng web server ang `index.php`.
  2. Walang `APP_KEY` na naka-set sa environment variables ng Render.
  3. Hindi pa naka-configure ang SSL CA options para sa remote TiDB Cloud database.
• Paano natin naayos?
  1. In-update natin ang Dockerfile gamit ang command na:
     `RUN sed -ri -e 's!/var/www/html!${APACHE_DOCUMENT_ROOT}!g' /etc/apache2/sites-available/000-default.conf`
     kung saan ang `APACHE_DOCUMENT_ROOT` ay naka-set sa `/var/www/html/public`.
  2. Ini-enable ang Apache `a2enmod rewrite`.
  3. Nag-generate tayo ng sariwang `APP_KEY` gamit ang `php artisan key:generate --show`
     at inilagay sa Render Environment Variables.
  4. Inayos ang `config/database.php` na magkaroon ng SSL attributes para sa TiDB Cloud.
  Resulta: 100% nag-boot at naging HTTP 200 OK ang website!

--------------------------------------------------------------------------------
CHALLENGE 2: ONEPASS OAUTH "400 BAD REQUEST" ERROR
--------------------------------------------------------------------------------
• Ano ang naging problema?
  Nang pindutin ang "Continue with OnePass SSO", nag-return ang OnePass server ng
  'Oops! The server returned a 400 Bad Request'.
• Bakit nag-error?
  Ang Redirect URI na ipinapadala ng aming local/production app ay hindi eksaktong
  tumutugma sa nakarehistro sa OnePass Developer Portal, at nagkaiba ang requested
  OIDC scopes.
• Paano natin naayos?
  1. Pumasok tayo sa OnePass Client Configuration at inilagay ang aming exactong
     production callback URL:
     `https://laravel-midterm-8n2y.onrender.com/oauth/callback`
  2. Sa OAuthController.php, in-align natin ang scope list na:
     `openid profile email student_id avatar`
  3. Ginamit ang pinakabagong Client ID at Client Secret.
  Resulta: Agad na lumabas ang official OnePass consent login screen kung saan
  pwedeng mag-login ang estudyante gamit ang kanilang campus account!

--------------------------------------------------------------------------------
CHALLENGE 3: SQLSTATE[23000] 1062 DUPLICATE ENTRY ERROR SA LOGIN
--------------------------------------------------------------------------------
• Ano ang naging problema?
  Nang mag-login si Jilo gamit ang OnePass SSO sa live website, lumabas ang error na:
  "SQLSTATE[23000]: Integrity constraint violation: 1062 Duplicate entry
  'jderramas251505@navotaspolytechniccollege.edu.ph' for key 'students.students_email_unique'
  insert into students (student_id, name, email ...) values (28, JILO DERRAMAS, ...)"
• Bakit nag-error?
  1. Sa aming TiDB database, may existing record na para kay Jilo Derramas na may
     email na `jderramas251505@navotaspolytechniccollege.edu.ph` at ang kanyang
     dating nakalistang student_id ay `251505`.
  2. Naka-set sa database structure na ang `email` column ay UNIQUE.
  3. Pagka-login sa OnePass, nagpadala ang OnePass ng ID na `28` (ang internal user
     account number niya sa OnePass).
  4. Sa lumang code ng OAuthController.php, ginamit ang:
     `Student::updateOrCreate(['student_id' => $studentId], [...])`
     Hinanap ng system kung may estudyanteng may ID na `28`. Dahil wala pa,
     inalisip ng system na bagong estudyante ito kaya nag-attempt mag-INSERT gamit
     ang email ni Jilo.
  5. Dahil umiiral na ang email na iyon sa database, humarang si MySQL/TiDB at
     nagtapon ng Duplicate Key error!
• Paano natin naayos?
  1. In-update natin ang student record sa TiDB database na maging `student_id = 28`
     upang maging consistent sa OnePass at sa lahat ng nauna niyang reservations.
  2. Inayos natin ang logic sa OAuthController.php:
     Sa halip na bulag na mag-updateOrCreate by student_id lang, gumawa tayo ng
     Smart Lookup:
     ```php
     $existingStudent = Student::where('email', $email)
         ->orWhere('student_id', $studentId)
         ->first();
     ```
     Kung may mahanap na student gamit ang email O student ID, iu-update na lang
     nito ang existing row nang walang duplicate insertion.
  3. Binalot natin ang database sync sa defensive `try / catch` block upang kahit
     magkaroon man ng delay o database warning, tuloy-tuloy pa rin ang session login
     at hinding-hindi na magka-crash ang screen ng user!
  Resulta: 100% smooth at instant ang sign-in process!

--------------------------------------------------------------------------------
CHALLENGE 4: REAL-TIME NOTIFICATIONS SA ACTIVITY LOGS (LOGIN / LOGOUT)
--------------------------------------------------------------------------------
• Ano ang naging problema?
  Gusto natin na tuwing may nag-lo-login o nag-lo-logout ang sinumang student o admin,
  makikita agad ito sa Activity Logs at magno-notify nang live sa Admin Console.
  Dati, hindi lumalabas ang notifications at kailangan pang mag-refresh ng page.
• Bakit nag-error / kulang?
  1. Sa `MerchController::getRealtimeSync`, hindi isinasama ang `activity_logs` sa
     JSON payload tuwing nagpo-poll ang frontend tuwing 2 segundo.
  2. Walang event listener o ID comparison sa frontend para matukoy kung may
     pumasok na bagong activity log.
  3. Walang dedicated Logout button ang Admin Console para ma-trigger ang `LOGOUT` audit log.
• Paano natin naayos?
  1. Sa `MerchController::getRealtimeSync`, kapag `scope === 'admin'`, isinama na
     ang pinakahuling 200 logs: `'activity_logs' => $activityLogs`.
  2. Sa `admin.blade.php`, sa loob ng `startAdminRealtimeSync()`, kinukumpara na
     ng frontend ang log ID laban sa `lastSeenActivityLogId`.
     Kapag may nakitang mas bagong log ID:
     - Nagpa-pop up agad ang live Floating Toast Notification sa screen:
       * 🔑 `[LOGIN] Student [...] authenticated successfully...`
       * 🚪 `[LOGOUT] Student [...] signed out of session...`
       * 📦 `[NEW] New reservation [...]`
     - Tumutunog ang Web Audio API synth chime sound.
     - Dynamic na inire-render ang Activity Logs Table sa Module 6 at ang Recent
       Activity Snippet sa Dashboard nang walang page reload!
  3. Nagdagdag tayo ng dedicated Admin Sign Out button sa header ng admin console
     na nagre-record ng `LOGOUT` sa database.
  4. Naglagay ng Activity Notification Bell sa header na may pulsing animated ping
     at live badge counter sa sidebar.
  Resulta: Real-time, interactive, at buhay na buhay ang buong Admin Console!
