TOPIC 2: CONTROLLERS & ARCHITECTURE (MerchController.php)
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Dumako naman po tayo sa Controller layer, partikular sa `app/Http/Controllers/MerchController.php`.
Dito po ipinatupad ang 'Single Responsibility' at 'Fat Model / Slim Controller' best practices.
Ang MerchController po ang humahawak sa orchestration ng data sa pagitan ng HTTP Requests 
at ng aming Eloquent Database Models.

Kapag tumanggap po ng request ang controller, ito ay dumadaan sa tatlong mahigpit na yugto:
1. Inbound Request Sanitization at Validation;
2. Database Transaction Execution gamit ang Eloquent ORM;
3. JSON o View Response Formatting na may kasamang HTTP Status Codes (tulad ng 200 OK, 
   201 Created, 403 Forbidden, 422 Unprocessable Content, o 500 Server Error).

Halimbawa po sa aming Real-time Live Chat Helpdesk:
Mayroon po kaming method na `getTicketMessages()` kung saan naglagay kami ng incremental 
query optimization gamit ang parameter na `after_id`. Sa pamamagitan po nito, hindi na 
hinihila ng server ang buong history ng chat tuwing nagpo-poll ang browser; tanging ang mga 
bagong mensahe na may ID na mas mataas sa `after_id` ang kinukuha. Dahil dito, ang database 
execution time ay bumaba sa sub-millisecond (2ms to 3ms) nang walang server bottleneck."

TOPIC 4: AUTHENTICATION & ONEPASS OIDC OAUTH INTEGRATION
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Isa po sa pinaka-advanced na feature ng aming backend ay ang aming Enterprise-grade Authentication.
Hindi po kami simpleng nag-hardcode ng login, kundi nagpatupad kami ng dalawang tier ng seguridad:

1. ADMIN AUTHENTICATION (Traditional Session & Database Auth):
   - Naka-store po ang mga awtorisadong admin officers sa aming `users` table.
   - Ang mga password po ay naka-hash gamit ang Bcrypt (Blowfish cipher) na may work factor 
     na 12, kaya imposible itong mabasa o ma-reverse kahit ma-access ang database.

2. STUDENT ONEPASS OAUTH 2.0 / OIDC (OpenID Connect with PKCE S256):
   - Sa halip na mag-retype pa ng credentials ang mga estudyante, ikinonekta po namin ang system 
     sa centralized OnePass Authorization Server sa pamamagitan ng `OAuthController.php`.
   - Gumamit po kami ng PKCE (Proof Key for Code Exchange) gamit ang SHA-256 hash algorithm 
     upang maiwasan ang authorization code interception attacks.
   - Kapag na-authorize ang estudyante sa OnePass, ipinagpapalit po ng aming backend ang 
     authorization code para sa isang secure Access Token at ID Token.
   - Matapos ma-verify ang cryptographically signed payload, kusa pong sine-sync ng controller 
     ang pangalan, student ID number, departamento (AIS), at email sa aming local session."

TOPIC 5: SERVER-SIDE VALIDATION & BUSINESS RULES
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Panghuli po sa Backend ay ang aming Server-side Validation.
Mahigpit po naming sinusunod ang panuntunan na: 'Never trust user input from the client.'
Lahat po ng papasok na data ay dumadaan sa `$request->validate()`:

1. Stock Availability Check sa `storeReservation()`:
   - Bago i-save ang order, sinusuri ng controller kung ang bawat napiling sukat 
     (XS, S, M, L, XL, 2XL, 3XL) ay may sapat pang available stock. Kung 0 na ang stock, 
     magbabalik ang server ng HTTP 422 na may malinaw na mensahe: 'Insufficient stock for size [M]'.
2. Anti-Spam at Chat Ticket Lock sa `storeTicketMessage()`:
   - Kapag ang isang ticket ay minarkahan na ng Admin bilang 'Resolved', awtomatikong 
     haharangin ng backend ang pagpapadala ng bagong mensahe gamit ang validation rule:
     `if ($ticket->status === 'Resolved') return response()->json(['message' => 'Ticket is closed'], 422);`
3. Student Privacy Enforcement:
   - Ang bawat estudyante po ay maaari lamang magbasa at mag-post sa ticket na nakatali 
     sa kanilang sariling Student ID number. Kapag nagtangkang mag-access ang ibang user 
     ng ticket ng iba, magbabalik po agad ang server ng HTTP 403 Unauthorized.

TOPIC 6: REAL-WORLD BUG FIXING & SECURITY ENHANCEMENTS
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Gusto ko rin pong ibahagi sa panel ang isang mahalagang challenge na matagumpay 
naming naayos sa Backend nitong nakaraan:

1. Ang SQL Duplicate Key Constraint Fix sa OnePass SSO:
   - Nung nag-login po ang student gamit ang OnePass, nagpadala ang OnePass ng 
     panloob na user ID na '28', ngunit sa aming database ay may nauna nang record 
     ang estudyante gamit ang kanyang institutional email at ID na '251505'.
   - Dahil UNIQUE ang email sa `students` table, nagtapon ng SQL Integrity Constraint 
     Violation (Error 1062) ang lumang `updateOrCreate(['student_id' => 28])` dahil inakala 
     nitong bagong student at nag-attempt mag-INSERT ng kaparehong email.
   - Ang ginawa po naming backend solution sa `OAuthController.php`:
     Gumawa kami ng Smart Lookup gamit ang `where('email', $email)->orWhere('student_id', $studentId)`.
     Kapag may nakitang existing record, safe update lang ng fields ang isinasagawa 
     sa halip na illegal duplicate insertion, at binalot sa defensive `try-catch` 
     para 100% crash-proof ang login.

2. Real-Time Activity Audit Delivery sa `/api/realtime/sync`:
   - In-upgrade din po namin ang `getRealtimeSync()` sa `MerchController.php`. 
     Kapag admin ang nagpo-poll, awtomatikong isinasama ng controller ang latest 
     `activity_logs` sa JSON response bawat 2 segundo, kaya nakakatanggap ang 
     admin console ng live real-time notifications kapag may nag-login, nag-logout, 
     o gumawa ng bagong reservation nang walang kailangang page refresh.

3. Dedicated Admin Sign-Out sa `routes/web.php`:
   - Nagdagdag kami ng `POST /admin/logout` endpoint na nagre-record ng 'LOGOUT' action 
     sa `activity_logs` at nagpu-purge ng session data bago i-redirect ang user."

IV. Q&A DEFENSE CHEAT SHEET (MGA POSIBLENG ITANONG NG PROF & SAGOT MO)
================================================================================
TANONG 1: "Bakit kayo gumamit ng Controller sa halip na ilagay ang logic sa routes/web.php?"
SAGOT MO:
"Para po sa Separation of Concerns at Maintainability. Ang routes/web.php po ay dapat 
nagsisilbi lamang na request router. Kapag inilagay po natin ang database queries at validation 
sa routes closure, magiging mahirap mag-unit test, madaling magka-duplicate code, at hindi 
masusunod ang MVC (Model-View-Controller) architecture na standard sa Laravel."

TANONG 2: "Paano ninyo pinoprotektahan ang API laban sa SQL Injection?"
SAGOT MO:
"Hindi po kami gumagamit ng raw SQL string concatenation tulad ng lumang PHP. Gumagamit po kami 
ng Laravel Eloquent ORM at Query Builder na may built-in PDO Prepared Statements at Parameter 
Binding. Ang lahat po ng parameters ay tinatrato bilang literals at hindi executable SQL commands."

TANONG 3: "Bakit `after_id` ang ginamit ninyo sa polling ng chat sa halip na i-load lahat?"
SAGOT MO:
"Para po sa Performance Optimization at para maiwasan ang server lag. Kapag 50 messages na 
ang nasa chat, kung kukunin lahat iyon tuwing 1 segundo, magiging mabigat ang JSON payload 
at database bandwidth. Gamit ang `WHERE id > after_id`, tanging 0 hanggang 1 bagong mensahe 
ang binabalik ng MySQL sa loob ng 2ms lamang nang walang pagsikip sa server."
