--------------------------------------------------------------------------------
TOPIC 1: DATABASE DESIGN & ENTITY-RELATIONSHIP ARCHITECTURE (ERD)
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Magsimula po tayo sa pangkalahatang Database Architecture.
Ang aming application po ay tumatakbo sa MySQL Relational Database Server gamit 
ang InnoDB Storage Engine. Binubuo po ito ng pitong (7) magkakaugnay na tables:

1. `products` (Master table ng mga merchandise apparel, SKU, presyo, at size stock).
2. `reservations` (Transaction table ng bawat naisagawang order ng estudyante).
3. `support_tickets` (Helpdesk inquiry records na nakakabit sa student o reservation).
4. `support_messages` (One-to-Many child table ng messages sa bawat support ticket).
5. `students` (Student profile master records na naka-sync sa OnePass).
6. `users` (Administrative staff at student user login credentials).
7. `activity_logs` (System-wide audit trail logs ng bawat CRUD action).

CARDINALITY AT FOREIGN KEY RELATIONSHIPS:
- Ang `support_tickets` po at `support_messages` ay may '1-to-Many (1:N)' relationship:
  Isang ticket ay may maramihang messages. Nakakabit po ang `support_messages.ticket_id` 
  sa `support_tickets.id` gamit ang Foreign Key na may `ON DELETE CASCADE`.
- Ang `reservations` at `support_tickets` ay may logical reference link sa pamamagitan 
  ng `reservation_ref`, kaya madaling ma-trace ng admin kung aling order ang may dispute.
- Sinunod po namin ang Third Normal Form (3NF) upang walang repeating columns at walang 
  transitive dependencies."

TOPIC 3: COLUMN TYPES & SCHEMA MODIFIERS
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Pagtuunan naman po natin ng pansin ang mga specific Column Types at Modifiers 
na aming ginamit upang masiguro ang matatag na data integrity:

1. Primary Keys & Foreign Keys:
   - `$table->id()`: Gumagawa ng auto-incrementing `BIGINT UNSIGNED` primary key.
   - `$table->foreignId('ticket_id')->constrained('support_tickets')->cascadeOnDelete()`:
     Lumilikha ng foreign key constraint na awtomatikong naglilinis ng mga lumang messages 
     kapag binura ang mother ticket (`ON DELETE CASCADE`), upang maiwasan ang orphan records.

2. Uniqueness Constraints:
   - `$table->string('item_code')->unique()` (hal. ICS-101)
   - `$table->string('ref_code')->unique()` (hal. REF-2026-10492)
   - `$table->string('ticket_code')->unique()` (hal. TKT-88412)
   Pinipigilan po nito ang pagkakaroon ng duplicate codes sa antas pa lamang ng database engine.

3. Structured JSON Datatype:
   - `$table->json('sizes')`: Sa `products` table, iniimbak ang dynamic size-to-stock mapping 
     (hal. `{"XS": 15, "S": 20, "M": 25, "L": 10}`).
   - `$table->json('items')`: Sa `reservations` table, iniimbak ang 'JSON Snapshot Pattern' 
     ng inorder na apparel kasama ang presyo at sukat sa oras ng pag-reserve. Sa ganitong 
     paraan, kahit magtaas ng presyo ang produkto sa hinaharap, hindi magbabago ang historical 
     voucher ng student.

4. Numerical Precision & Enumerated States:
   - `$table->decimal('price', 10, 2)`: Tumpak na floating point para sa pera (hal. ₱350.00) 
     nang walang rounding errors.
   - `$table->enum('status', ['Pending', 'Ready for Pickup', 'Claimed', 'Cancelled'])->default('Pending')`:
     Nagtatakda ng mahigpit na state machine sa mga reservation."

ANO ANG IPAKIKITA MO SA SCREEN:
- I-highlight ang lines sa migration file na may `$table->json(...)`, `$table->unique()`, 
  at `$table->foreignId()->cascadeOnDelete()`.

TOPIC 4: .ENV CONFIGURATION PARA SA DATABASE
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Tingnan naman po natin ang configuration layer sa aming `.env` file.
Sinunod po namin ang Twelve-Factor App methodology kung saan ang lahat ng database credentials 
ay nakahiwalay sa environment variables sa halip na i-hardcode sa application logic:

`DB_CONNECTION=mysql`
`DB_HOST=127.0.0.1`
`DB_PORT=3306`
`DB_DATABASE=my_laravel`
`DB_USERNAME=root`
`DB_PASSWORD=`

Bakit po ganito?
1. Security: Ang `.env` file po ay nakalista sa aming `.gitignore`, kaya kailanman ay 
   hindi mai-a-upload ang sensitibong database passwords sa pampublikong GitHub repository.
2. Portability: Madali po naming maililipat ang database papunta sa production cloud database 
   tulad ng Supabase, PlanetScale, o AWS RDS sa pamamagitan lamang ng pagpapalit ng host 
   at port sa `.env`, nang hindi binabago ang kahit isang linya ng PHP code sa application."

ANO ANG IPAKIKITA MO SA SCREEN:
- Buksan ang `.env` file at ituro ang `DB_*` block ng lines.

TOPIC 5: MIGRATION MANAGEMENT, SEEDERS, AT ACID COMPLIANCE
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Panghuli po sa Database Administration ay ang aming Migration Management at ACID Compliance:

1. Database Seeding (IcsDatabaseSeeder.php):
   - Upang masubukan agad ang system nang may makatotohanang data sa defense, lumikha po kami 
     ng komprehensibong database seeder sa `database/seeders/IcsDatabaseSeeder.php`.
   - Sa pamamagitan ng pagpapatakbo ng:
     `php artisan migrate:fresh --seed`
     kusa pong itinatayo ng Laravel ang lahat ng tables at pinupuno ito ng opisyal na 
     ICS polo uniforms, department shirts, test student accounts, initial stock, at activity logs.

2. InnoDB ACID Compliance (Data Protection):
   - Ang aming MySQL database po ay gumagamit ng InnoDB engine na may ACID compliance:
     * Atomicity: Kapag nag-reserve ang student, sabay na binabawasan ang stock sa `products` 
       at inililista ang reservation sa `reservations`. Kung magka-error ang isa, magro-rollback 
       ang transaction upang walang masayang na damit.
     * Durability: Kapag nai-commit na ang reservation sa pamamagitan ng Eloquent, permanente 
       na itong nakasulat sa storage disk at hindi mawawala kahit mag-brownout o mag-restart 
       ang laptop."

TOPIC 6: TIDB SERVERLESS CLOUD MIGRATION & UNIQUE CONSTRAINT INTEGRITY
--------------------------------------------------------------------------------
ANO ANG SASABIHIN MO:
"Gusto ko rin pong ibahagi sa panel ang aming Cloud Database Migration at Data Integrity:

1. TiDB Serverless Cloud Database (AWS Singapore):
   - Hindi po kami nanatili sa local MySQL ng XAMPP. Matagumpay po naming inilipat 
     ang buong schema at seed data sa TiDB Serverless Cloud Database 
     (`gateway01.ap-southeast-1.prod.aws.tidbcloud.com:4000`).
   - Naka-enable po ang secure TLS/SSL database tunneling gamit ang 
     `PDO::MYSQL_ATTR_SSL_CA => true` sa `config/database.php`.
   - Dahil dito, 24/7 accessible ang aming data mula sa internet at naka-sync 
     ang live Render application sa iisang centralized cloud database.

2. Handling Unique Constraint Collisions (`students_email_unique`):
   - Noong mag-login po ang student gamit ang OnePass OAuth, nagkaroon po ng pagsubok:
     nagpadala ang OnePass ng ID na '28' habang ang record sa database ay may ID na '251505'.
   - Dahil may UNIQUE constraint ang `email` column sa `students` table, sinadyang 
     harangin ng database engine ang duplicate row insertion (SQLSTATE 1062).
   - Bilang DBA, nakipagtulungan po ako sa backend upang i-align ang student_id 
     at magpatupad ng smart query check (`orWhere`) upang mapanatili ang integridad 
     ng data nang walang data duplication o integrity corruption."

IV. Q&A DEFENSE CHEAT SHEET (MGA POSIBLENG ITANONG NG PROF & SAGOT MO)
================================================================================
TANONG 1: "Bakit JSON column ang ginamit ninyo para sa sizes sa halip na gumawa ng hiwalay na product_sizes table?"
SAGOT MO:
"Magandang tanong po. Ginamit po namin ang JSON column sa ilalim ng tinatawag na 'Document-Store within RDBMS Pattern'. 
Dahil ang mga sukat (XS hanggang 3XL) ay static attributes lamang ng bawat apparel at hindi kailangang 
i-query nang hiwalay sa labas ng produkto, ang JSON column ay nagbibigay ng mas mabilis na read performance 
dahil hindi na kailangan ng mabigat na SQL `JOIN` operation tuwing bubuksan ang merchandise catalog."

TANONG 2: "Ano ang silbi ng `ON DELETE CASCADE` sa inyong foreign key?"
SAGOT MO:
"Pinipigilan po nito ang pagkakaroon ng 'Orphan Records' o mga basurang data sa database. 
Halimbawa po, kung buburahin ng admin ang isang Support Ticket, kusa ring buburahin ng MySQL engine 
ang lahat ng nakakabit na messages sa ticket na iyon sa ilalim ng `support_messages` table nang hindi 
nag-iiwan ng sirang dayuhang datos."

TANONG 3: "Kung magkakaroon kayo ng bagong migration, paano niyo ito idadagdag nang hindi nabubura ang laman ng database?"
SAGOT MO:
"Gagawa po kami ng panibagong migration file gamit ang:
`php artisan make:migration add_new_column_to_table --table=table_name`
at gagamit kami ng `Schema::table()` sa halip na `Schema::create()`. 
Pagkatapos ay patatakbuhin lamang namin ang `php artisan migrate`. Sa paraang ito, idaragdag lamang 
ang bagong column nang hindi nagkakaroon ng data loss sa mga umiiral nang records."
