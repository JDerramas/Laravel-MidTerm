I. TUNGKULIN NG DATABASE ARCHITECT SA DEFENSE
--------------------------------------------------------------------------------
Kung ikaw ang nakatoka sa Database, ikaw ang sasagot sa lahat ng tanong tungkol sa:
1. Paano naka-store ang data sa MySQL at bakit ganoon ang design ng mga tables.
2. Ano ang relasyon ng bawat table (ERD / Cardinality: One-to-Many, Foreign Keys).
3. Paano pinoprotektahan ang data laban sa corruption, orphan records, at SQL injection.
4. Bakit gumamit ng Eloquent ORM Models sa halip na raw SQL queries.
5. Bakit ginamit ang "JSON Snapshot Pattern" para sa shopping cart items at sizes.


================================================================================
II. DATABASE ENGINE AT ACID COMPLIANCE
--------------------------------------------------------------------------------
1. Database Engine: MySQL gamit ang InnoDB Storage Engine.
   - Character Set: utf8mb4 (sumusuporta sa complete Unicode kabilang ang emojis).
   - Collation: utf8mb4_unicode_ci (case-insensitive para sa mabilis na paghahanap).

2. Bakit InnoDB at may ACID Compliance?
   - Atomicity (Lahat o Wala): Kapag nag-checkout ang student, sabay na binabawasan
     ang stock at ginagawa ang reservation. Kung mag-fail ang isa, magro-rollback
     ito para walang nawawalang damit.
   - Consistency: Sinisiguro ng Foreign Keys at Unique Constraints (ref_code,
     item_code, ticket_code) na laging sumusunod sa business rules ang bawat row.
   - Isolation: Kahit sabay-sabay mag-order o mag-chat ang 100 estudyante, hindi
     magkakahalu-halo ang kanilang session at hindi makakabasa ng "dirty data".
   - Durability: Kapag na-save na ang order sa MySQL, permanent na ito sa hard drive
     at hindi mawawala kahit mamatay ang kuryente o mag-restart ang XAMPP server.

• PALIWANAG SA RELASYON:
  1. support_tickets (1) to support_messages (N):
     - One-to-Many. Isang ticket, maraming palitan ng chat messages.
     - Foreign Key: `ticket_id` sa support_messages naka-link sa `id` ng support_tickets.
     - Constraint: `onDelete('cascade')` — kapag binura ang resolved ticket,
       awtomatikong binubura rin lahat ng kaakibat na messages para walang "orphan records".

  2. reservations (1) to support_tickets (N):
     - Naka-link gamit ang `reservation_ref` (Foreign reference patungo sa `ref_code`).
     - Sa Eloquent: `$reservation->supportTickets()` (HasMany) at `$reservation->activeTicket()`
       (HasOne conditional kung saan status is 'Open' o 'In Progress').

  3. products (1) to reservations (N):
     - Naka-ugnay sa pamamagitan ng **JSON Snapshot Pattern**. Sa halip na gumawa
       ng mabagal na pivot table, iniimbak ng reservation ang buong detalye ng
       mga damit sa oras ng checkout.

• 1-Paragraph Summary:
Basically, ito ang opisyal na imbentaryo ng tindahan. V. MGA ARCHITECTURAL DECISIONS (BAKIT GANITO ANG SCHEMA DESIGN?)
================================================================================

1. BAKIT JSON DATA TYPE ANG GINAMIT SA `sizes` AT `items`?
   - Question ng Panel: "Bakit hindi kayo gumawa ng hiwalay na reservation_items table at product_sizes table?"
   - Sagot ng Database Architect:
     a) Snapshot Pattern: Kapag nagbago ang presyo ng polo mula ₱400 naging ₱450 sa susunod na buwan, ang lumang reservation ay dapat ₱400 pa rin. Kung relational join ito sa products table, magkakaroon ng historical price corruption.
     b) Performance sa Realtime Polling: Tumatawag ang frontend sa API bawat 3 segundo. Kung may 4-table relational join bawat 3 segundo, bibigat ang query execution. Dahil naka-JSON, single-table read lang ang kailangan kaya sub-millisecond ang response time.
     c) MySQL Native JSON Support: May built-in JSON indexing at verification ang MySQL 8 at madaling i-cast ng Laravel bilang PHP array via `protected $casts = ['items' => 'array']`.

2. BAKIT MAY INDEXES ANG student_id, reservation_ref, AT status?
   - Indexing creates a B-Tree structure sa MySQL disk storage.
   - Dahil libu-libong estudyante ang pwedeng maghanap ng order gamit ang student_id o reference code, ang indexed query ay tumatagal lang ng O(log N) sa halip na mag-Full Table Scan ng O(N).

3. PAANO NAIWASAN ANG ORPHAN RECORDS SA CHAT HELPDESK?
   - Ginamitan ng `onDelete('cascade')` ang `support_messages` foreign key:
     `$table->foreignId('ticket_id')->constrained('support_tickets')->onDelete('cascade');`
   - Kapag binura ang isang resolved ticket, awtomatikong nililinis ng MySQL ang lahat ng messages nito nang sabay, kaya walang naiiwanang "ghost messages" sa database.

VI. ELOQUENT ORM MODELS, CASTS, AT RELATIONSHIPS (app/Models/*)
================================================================================

1. Product.php:
   - `protected $fillable`: Proteksyon laban sa Mass Assignment Vulnerability.
   - `protected $casts = ['sizes' => 'array', 'is_active' => 'boolean']`:
     Kusang kino-convert ni Laravel ang JSON string mula sa MySQL para maging associative array agad sa PHP nang hindi na kailangang mag-`json_decode()`.

2. Reservation.php:
   - `protected $casts = ['items' => 'array']`:
     Array agad ang listahan ng mga biniling damit kapag kinuha sa database.
   - `public function supportTickets()`:
     HasMany relationship sa `SupportTicket` gamit ang `reservation_ref` at `ref_code`.
   - `public function activeTicket()`:
     HasOne relationship na nagpi-filter kung may tiket na may status na `Open` o `In Progress` para sa automatic ON HOLD lock sa queue.

3. SupportTicket.php:
   - `public function messages()`:
     HasMany relationship patungo sa `SupportMessage`, naka-order ayon sa `created_at` asc para tuloy-tuloy ang convo.
   - `public function reservation()`:
     BelongsTo relationship pabalik sa `Reservation` gamit ang `reservation_ref`.

4. SupportMessage.php:
   - `public function ticket()`:
     BelongsTo relationship na kumikilala kung saang ticket thread nabibilang ang chat bubble.

5. ActivityLog.php:
   - Naglalaman ng static helper method:
     `ActivityLog::record($action, $activity, $userCode, $userName, $module);`
     Pinapadali nito ang pagtatala sa audit trail mula sa kahit saang controller nang isang linya lamang.

VIII. TOP 10 DATABASE DEFENSE QUESTIONS & PANELIST TRICK QUESTIONS (MGA SAGOT)
================================================================================

Q1: "Bakit MySQL ang ginamit ninyong database at hindi MongoDB o NoSQL?"
A: "Kasi po ang Apparel Reservation System ay isang transaksyonal na application kung saan kritikal ang ACID compliance at financial accuracy. Sa MySQL, mayroon tayong mahigpit na data types, foreign key constraints, at table relationships na sumisiguro na hindi magkakaroon ng duplicate reference codes o overbooked na imbentaryo. Ang NoSQL tulad ng MongoDB ay mas angkop sa un-structured big data, samantalang ang aming e-commerce inventory ay likas na relational."

Q2: "Paano ninyo pinoprotektahan ang database laban sa SQL Injection attacks?"
A: "Gumagamit po kami ng Laravel Eloquent ORM at PDO Parameter Binding. Sa halip na mag-concatenate ng raw strings sa queries, si Laravel ay nagpapadala ng hiwalay na query template at sanitized parameters sa MySQL engine. Halimbawa, sa `Product::where('item_code', $code)->first()`, awtomatikong ine-escape at bina-bind ang input kaya imposible itong ma-infiltrate ng SQL injection."

Q3: "Bakit may JSON columns (sizes at items) kung relational database ang MySQL? Hindi ba lumalabag ito sa First Normal Form (1NF)?"
A: "Sinasadya po namin itong tinatawag na 'Controlled Denormalization' gamit ang MySQL native JSON features. Sa pamantayan ng First Normal Form, atomic dapat ang values, subalit sa modernong e-commerce architecture tulad ng Shopify, ginagamit ang Snapshot Pattern sa mga orders. Kung bawat damit sa cart ay gagawan pa ng hiwalay na reservation_items row, kakailanganin namin ng mabibigat na multi-table JOINs tuwing tatakbo ang 3-second realtime sync engine. Dahil naka-JSON snapshot ito, napakabilis ng read speed at napoprotektahan ang lumang order history laban sa price fluctuations kapag nagtaas ng presyo ang damit sa hinaharap."

Q4: "Ano ang mangyayari sa database kapag may binurang resolved support ticket?"
A: "Dahil naka-configure po ang aming migration gamit ang `$table->foreignId('ticket_id')->constrained('support_tickets')->onDelete('cascade')`, kapag binura ang row sa `support_tickets`, awtomatikong binubura rin ng MySQL engine ang lahat ng kaakibat nitong chat messages sa `support_messages` table sa iisang atomic operation. Naiiwasan nito ang pagkakaroon ng orphan o ghost records sa database."

Q5: "Bakit bawal burahin ang ticket kung hindi pa ito Resolved?"
A: "Proteksyon po ito sa data integrity. May validation check sa controller na sumusuri kung `$ticket->status !== 'Resolved'`. Kung 'Open' o 'In Progress' pa ito, bina-block ng server ang DELETE request upang maiwasan ang aksidenteng pagkawala ng aktibong reklamo o concern ng estudyante habang inaasikaso pa ng admin."

Q6: "Ano ang silbi ng Unique Constraints sa inyong database schema?"
A: "May apat po kaming pangunahing Unique Constraints:
   1. `products.item_code` (e.g. 'ICS-POLO-M') para walang duplicate SKU.
   2. `reservations.ref_code` (e.g. 'ICS-2026-X941K') para garantisadong natatangi ang bawat claim ticket.
   3. `support_tickets.ticket_code` (e.g. 'TCK-2026-0001') para sa tracking.
   4. `system_users.user_code` at `email` para walang magkaparehong staff account.
   Kahit sabay-sabay mag-checkout ang mga estudyante, hinding-hindi papayag ang MySQL na magkaroon ng duplicate records."

Q7: "Bakit DECIMAL(10,2) ang ginamit sa presyo at hindi FLOAT o DOUBLE?"
A: "Ang FLOAT at DOUBLE po ay inexact floating-point representations sa computer memory na nagdudulot ng rounding errors (halimbawa: 0.1 + 0.2 ay nagiging 0.30000000000000004). Sa pananalapi at reservation total amounts, kailangan ng exact precision. Ang DECIMAL(10,2) ay iniimbak ng MySQL bilang exact fixed-point string, kaya garantisadong hanggang dalawang decimal places lamang at 100% accurate sa sentimo."

Q8: "Paano ninyo nalalaman kung sinong admin ang nagbura o nagbago ng stock sa database?"
A: "Mayroon po kaming dedicated `activity_logs` table na gumaganap bilang Audit Trail. Tuwing may nagaganap na CREATE, READ, UPDATE, o DELETE sa pamamagitan ng controller, awtomatikong tumatawag ang system sa `ActivityLog::record()`. Itinatala nito ang user_code, timestamp, IP address, module, at detalyadong aksyon upang laging may pananagutan ang bawat galaw."

Q9: "Ano ang ginagawa ng database kapag nag-cancel ng order ang estudyante sa pamamagitan ng support ticket?"
A: "Sa loob ng iisang controller transaction:
   1. Hinahanap ang reservation record at binabago ang status nito patungong 'Cancelled'.
   2. Binabasa ang JSON `items` snapshot at awtomatikong idinaragdag pabalik ang dami sa `current_stock` ng bawat damit at sa kaukulang `sizes` array.
   3. Binabawasan ang `units_reserved`.
   4. Minamarkahang 'Resolved' ang support ticket.
   5. Nagpapasok ng automated system notification message sa chat thread at nagre-record sa `activity_logs` table."

Q10: "Kung magdadagdag kayo ng bagong column sa database sa production, paano ninyo ito gagawin nang hindi nabubura ang existing records?"
A: "Gagawa po kami ng panibagong Laravel migration file gamit ang `php artisan make:migration add_new_column_to_table`. Sa loob ng `up()` method, gagamitin namin ang `Schema::table()` sa halip na `Schema::create()`. Pagkatapos, patatakbuhin ang `php artisan migrate`. Sa ganitong paraan, idaragdag lamang ang bagong column nang ligtas at hindi magagalaw o mawawala ang mga kasalukuyang datos ng mga estudyante."
