1. QUICK TERMINOLOGY GUIDE (NO CONFUSING SHORTCUTS)
================================================================================

When explaining database architecture to an academic panel or client, use clear,
formal terms instead of confusing acronyms:

* PRIMARY KEY (PK):
  - The unique identifier for every single row in a table. It is typically an
    auto-incrementing integer ID (1, 2, 3...) that guarantees every record can
    be retrieved directly and without ambiguity.

* UNIQUE KEY (UK) / UNIQUE CONSTRAINT:
  - A database rule that prevents duplicate values in a column across the entire
    table. For example, Reference Codes (`ref_code`) and Student IDs (`student_id`)
    are Unique Keys so that two orders or students can never share the same code.

* FOREIGN KEY (FK):
  - A relational bridge linking a child record to its parent row in another table.
    For example, `support_messages.ticket_id` is a Foreign Key referencing
    `support_tickets.id`.

* ONE-TO-MANY RELATIONSHIP (1 : N):
  - A data relationship where one parent record can be associated with multiple
    child records. For example: ONE Support Ticket can contain MANY Chat Messages.

* CASCADING DELETION (`ON DELETE CASCADE`):
  - An automated database cleanup rule. When a parent record (such as a Support
    Ticket) is deleted, the database automatically deletes all of its connected
    child records (such as its chat messages) in a single operation. This ensures
    there are no orphan or ghost records left cluttering storage.

* ACID TRANSACTIONS (Atomicity, Consistency, Isolation, Durability):
  - The gold standard for financial and inventory safety. It guarantees that multi-step
    operations (like deducting stock and creating an order) succeed completely or fail
    completely, with zero risk of partial, corrupted data.

2. DATABASE ENGINE & ACID COMPLIANCE OVERVIEW
================================================================================

* Database Engine: MySQL powered by the InnoDB Storage Engine.
* Character Set  : `utf8mb4` (supports complete Unicode, international characters,
                   and modern emojis in support chat).
* Collation      : `utf8mb4_unicode_ci` (case-insensitive for fast, natural searching).

Why InnoDB and ACID Compliance?
--------------------------------------------------------------------------------
1. ATOMICITY ("All or Nothing"):
   - When a student checks out, the system must simultaneously deduct stock from
     the `products` table and insert a new order record into `reservations`. If an
     error occurs halfway through (such as a network drop or insufficient funds),
     the database automatically rolls back all changes. No merchandise is ever lost.

2. CONSISTENCY:
   - Foreign Keys and Unique Constraints enforce business rules at the database
     level, guaranteeing that invalid data cannot be saved even if a client bypasses
     frontend checks.

3. ISOLATION:
   - Even if dozens of students check out or chat at the exact same second during
     a flash merchandise sale, transactions are isolated. No user will ever see
     "dirty data" or uncommitted changes from another concurrent session.

4. DURABILITY:
   - Once an order or payment confirmation is written to disk, it is permanent.
     Even in the event of a sudden server crash or power failure, committed
     transactions remain intact and recoverable.

4. DETAILED BREAKDOWN OF THE 7 DATABASE TABLES
================================================================================

TABLE 1: `products` (The Merchandise Catalog)
--------------------------------------------------------------------------------
- Purpose: Stores all merchandise items available for reservation.
- Key Columns:
  * `id` (Primary Key): Auto-incrementing identifier.
  * `item_code` (Unique Key): Formal SKU, e.g. "POLO-001", "LANYARD-002".
  * `name`, `category`: Descriptive merchandise categorization.
  * `price` (DECIMAL 10,2): Exact financial unit price.
  * `sizes` (JSON): Dynamic breakdown of inventory quantities per size:
    `{"XS":10, "S":25, "M":40, "L":35, "XL":15, "2XL":5}`.
  * `current_stock` (INTEGER): Total units available across all sizes.
  * `image_url`: Relative path to the uploaded product photo in `/storage`.

TABLE 2: `reservations` (Student Checkout Orders)
--------------------------------------------------------------------------------
- Purpose: Stores all placed reservations, payment methods, and fulfillment states.
- Key Columns:
  * `id` (Primary Key): Unique reservation record identifier.
  * `ref_code` (Unique Key): High-entropy human-readable tracking code (e.g., `ICS-98214`).
  * `student_id`: Student number linking the order to the verified buyer.
  * `student_name`, `email`, `section`: Buyer contact information.
  * `items` (JSON Snapshot): Complete record of purchased products, sizes,
    unit prices, and quantities captured at the moment of checkout.
  * `total_amount` (DECIMAL 10,2): Grand total price of the reservation.
  * `payment_method`: "Cash" on pickup or "GCash" digital transfer.
  * `receipt_image`: Proof-of-payment screenshot uploaded by the student.
  * `status`: Order lifecycle enum (`Pending`, `Ready for Pickup`, `Claimed`, `Cancelled`).

TABLE 3: `support_tickets` (Student Inquiries & Complaints)
--------------------------------------------------------------------------------
- Purpose: Tracks student help requests and connects directly to specific orders.
- Key Columns:
  * `id` (Primary Key): Auto-incrementing ticket ID.
  * `ticket_code` (Unique Key): Tracking identifier, e.g., `TCK-104`.
  * `reservation_ref`: The reference code of the related order (`ICS-XXXX`).
  * `student_id`: Identity of the student raising the ticket.
  * `subject`, `description`: Details of the complaint or question.
  * `status`: `Open`, `In Review`, or `Resolved`.
  * Special Mechanism: When status is `Open` or `In Review`, it triggers the
    "Conflict Lock" (`⚠️ ON HOLD`) on the corresponding reservation.

TABLE 4: `support_messages` (Live Chat Transcripts)
--------------------------------------------------------------------------------
- Purpose: Stores conversational chat between students and council officers.
- Key Columns:
  * `id` (Primary Key): Unique message ID.
  * `ticket_id` (Foreign Key): Relational link to `support_tickets.id`.
    Enforced with `ON DELETE CASCADE`.
  * `sender_type`: Distinguishes who sent the message (`student` vs. `admin`).
  * `sender_name`: Display name of the sender.
  * `message` (TEXT): The actual chat content (supports Unicode and emojis).
  * `created_at`: Exact timestamp used for ordering and turn-taking anti-spam validation.

TABLE 5: `system_users` (Administrative Roster & RBAC)
--------------------------------------------------------------------------------
- Purpose: Roster of verified student council administrators and faculty advisers.
- Key Columns:
  * `id` (Primary Key): Unique staff ID.
  * `user_code` (Unique Key): Administrative personnel ID (e.g., `USR-010`).
  * `name`: Full name of the officer or adviser.
  * `email` (Unique Key): Campus email (e.g., `ics@npc.edu.ph`).
  * `role`: System authorization role (`Administrator` or `Staff`).
  * `status`: Account status (`Active` or `Inactive`).
  * Special Mechanism: Checked during the OnePass OIDC SSO login flow to grant
    or deny access to the `/admin` Operations Portal.

TABLE 6: `students` (Cached Verified Student Directory)
--------------------------------------------------------------------------------
- Purpose: Local cache of verified student identities authenticated via OnePass.
- Key Columns:
  * `id` (Primary Key): Unique student record ID.
  * `student_id` (Unique Key): Official institutional student number.
  * `email` (Unique Key): Verified institutional email.
  * `first_name`, `last_name`, `section`, `department`: Academic metadata.
  * `avatar_url`: Student profile photo synchronized from the campus SSO directory.

TABLE 7: `activity_logs` (Security & Audit Trail)
--------------------------------------------------------------------------------
- Purpose: Immutable audit ledger recording every critical system action.
- Key Columns:
  * `id` (Primary Key): Sequential log ID.
  * `user_code`: Identifier of the user who performed the action.
  * `action`: Action verb (`CREATE`, `UPDATE`, `DELETE`, `LOGIN`, `STATUS_CHANGE`).
  * `activity`: Detailed description of the event.
  * `module`: System area affected (`Products`, `Reservations`, `Support`, `Security`).
  * `created_at`: Exact immutable timestamp of the operation.

5. THE 4 KEY ARCHITECTURAL PATTERNS & DESIGN DECISIONS
================================================================================

1. THE JSON SNAPSHOT PATTERN (`reservations.items` & `products.sizes`):
   - Problem: In traditional databases, order line items are broken into a separate
     `reservation_items` table linked by product ID. However, if an administrator
     updates product pricing, changes fabric details, or deletes a discontinued item,
     past student receipts become inaccurate or broken.
   - Solution: We store the exact purchased items, sizes, unit prices, and quantities
     as a frozen JSON snapshot at the instant of order creation.
   - Benefit: Student receipts remain 100% historically immutable, independent of
     future catalog modifications, while drastically simplifying query overhead.

2. CASCADING FOREIGN KEY DELETION (`support_messages.ticket_id`):
   - Problem: Deleting a support ticket can leave thousands of orphaned messages in
     the database, consuming disk space and causing relational errors.
   - Solution: We configured `FOREIGN KEY (ticket_id) REFERENCES support_tickets(id) ON DELETE CASCADE`.
   - Benefit: When an administrator deletes a resolved support ticket, MySQL's InnoDB
     engine automatically and cleanly purges all related messages in a single atomic step.

3. ATOMIC INVENTORY ALLOCATION (InnoDB ACID TRANSACTIONS):
   - Problem: When two students attempt to purchase the last available shirt at the
     same second, a race condition can cause both orders to succeed, resulting in
     negative stock.
   - Solution: We wrap stock deduction and reservation insertion inside a database
     transaction (`DB::transaction()`).
   - Benefit: Stock is locked and verified during checkout. If another customer claims
     the last item first, the transaction rolls back gracefully and informs the buyer,
     guaranteeing zero overbooking.

4. THE CONFLICT LOCK MECHANISM (`⚠️ ON HOLD`):
   - Problem: A student might report an issue with their reservation (e.g., incorrect
     payment slip or wrong size requested) while a counter officer simultaneously
     marks the order as "Claimed".
   - Solution: The system cross-references `support_tickets` where `reservation_ref = reservations.ref_code`.
     If any ticket is in `Open` or `In Review` status, the reservation automatically
     locks into `⚠️ ON HOLD` state.
   - Benefit: Counter staff cannot accidentally release merchandise until the customer
     service issue is officially resolved.

"Good day, distinguished panelists and professors. I will now present the Database
Schema and Architectural Design of the ICS Apparel and Merchandise Reservation System.

Our database is built on MySQL using the InnoDB storage engine, which provides full
ACID compliance—guaranteeing that every financial transaction and inventory deduction
is atomic, consistent, isolated, and durable.

Our system is structured around 7 core tables:

1. First, the 'products' table serves as our merchandise catalog. Instead of using
   rigid column layouts, we utilize a dynamic JSON structure to store real-time
   inventory counts across individual sizes—from Extra Small to 2XL.

2. Second, the 'reservations' table manages all student orders. A key architectural
   decision here is the 'JSON Snapshot Pattern'. When a student checks out, the exact
   merchandise details, sizes, and prices are frozen into a native JSON snapshot.
   This guarantees that if product prices change in the future, past student receipts
   remain 100% historically accurate.

3. Third, our 'support_tickets' and 'support_messages' tables power our built-in student
   assistance portal. They are linked through a one-to-many relationship with cascading
   deletion. When a resolved ticket is removed, all associated chat messages are
   automatically purged by MySQL, preventing orphaned data.

4. Furthermore, we implemented an automated 'Conflict Lock'. If an open support ticket
   exists for an order, the system locks the reservation into an 'ON HOLD' status to
   prevent counter officers from releasing merchandise before disputes are resolved.

5. Fifth, the 'system_users' table houses authorized faculty and council officers,
   such as our primary administrator account, ics@npc.edu.ph. Access to our administrative
   portal is strictly protected through role-based access control.

6. Sixth, the 'students' table maintains cached profile records populated directly from
   verified OnePass OpenID Connect Single Sign-On authentications.

7. And finally, the 'activity_logs' table functions as our immutable security ledger,
   recording every creation, update, deletion, and authentication event with precise
   timestamps.

In conclusion, our schema was intentionally engineered to eliminate data corruption,
prevent inventory race conditions, and preserve receipt integrity. Thank you, and I am
now ready to answer any questions regarding our database design."

7. PANEL Q&A CHEAT SHEET (TOP QUESTIONS & PROFESSIONAL ANSWERS)
================================================================================

QUESTION 1:
"Why did you use a JSON snapshot for cart items instead of a normalized 'order_items' table?"

ANSWER:
"That is an intentional architectural pattern called the Document Snapshot Pattern.
In e-commerce, merchandise prices and descriptions evolve over time. If we had simply
linked orders to products by foreign key, any future price increase or product name
change would retroactively corrupt past student receipts. By storing an immutable JSON
snapshot at the moment of checkout, past orders remain 100% legally and historically
accurate forever, without requiring redundant relational tables."

---

QUESTION 2:
"How does your database prevent stock overselling when multiple students order at the same time?"

ANSWER:
"We enforce inventory integrity through InnoDB database transactions. When an order
is placed, the product deduction and order creation occur atomically. If stock drops
below zero or a concurrent request claims the last available unit first, the entire
transaction rolls back immediately. This guarantees that our stock numbers never desync
and prevents overbooking."

---

QUESTION 3:
"What happens to chat messages when an administrator deletes a support ticket?"

ANSWER:
"We configured the foreign key on `support_messages.ticket_id` with `ON DELETE CASCADE`.
This means the MySQL database engine handles cleanup automatically. The instant a ticket
is deleted, all connected chat messages are purged in a single atomic database operation,
ensuring zero orphan records."

---

QUESTION 4:
"How do you protect your database against SQL Injection attacks?"

ANSWER:
"Our entire data access layer is powered by Laravel's Eloquent ORM and PDO query builder.
Every query uses 100% parameterized binding under the hood. User inputs are never
concatenated directly into SQL queries, rendering SQL injection attempts completely
ineffective."

---

QUESTION 5:
"What is the Conflict Lock mechanism and how is it reflected in the database?"

ANSWER:
"The Conflict Lock is a safeguard between `support_tickets` and `reservations`. When a
student opens a ticket regarding an order, the system queries the database for active
tickets linked to that order's reference code. If any ticket has a status of 'Open' or
'In Review', the reservation displays an 'ON HOLD' lock in both the student tracker
and the admin portal. This prevents officers from releasing goods while a customer
inquiry is still unresolved."
