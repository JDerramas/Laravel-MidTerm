[YUGTO 1: OPENING & PROBLEM STATEMENT] - Nagsasalita: MEMBER 1
--------------------------------------------------------------------------------
MEMBER 1:
"Magandang araw po sa ating guro at sa mga panelist. Kami po ang Grupo [Ilagay ang Group Number o Pangalan] mula sa AIS, at ipinagmamalaki po naming i-present ang aming Midterm Capstone Project: ang 'ICS Apparel & Merchandise Reservation System'.

Ang Integrated Computer Society po taun-taon ay nahaharap sa logistics issues sa pamamahagi ng department uniforms, P.E. shirts, at org lanyards. Ang lumang paraan po ng manual sign-up sa papel o Google Forms ay nagdudulot ng:
1. Double-booking at maling bilang ng stock bawat sukat.
2. Kawalan ng transparent tracking kung kailan kukunin ang damit.
3. Logistics deadlocks kung saan nakaka-claim ang student kahit may unresolved dispute pa sa order.

Upang lutasin ito, binuo po namin ang isang enterprise-grade, full-stack Laravel 11 application na may realtime sync, automated conflict lock, at turn-taking customer support. Bago po namin ipaliwanag ang backend at database architecture, hayaan po muna naming ipakita ang live flow ng application."


--------------------------------------------------------------------------------
[YUGTO 2: THE 7-STEP LIVE DEMONSTRATION] - Nagsasalita: MEMBER 1 & MEMBER 2
--------------------------------------------------------------------------------
(I-share ang screen: Dalawang browser window ang bukas — Kaliwa: Student Store `/`, Kanan: Admin Portal `/admin`)

HAKBANG 1 (OnePass Campus Single Sign-On & Unified Header - Member 1):
"Dito po sa kaliwa ay ang Student Storefront. Pansinin po ninyo sa header ang aming 'Student Login (OnePass)' button. Sa halip po na mag-type ng username at password ang student, mayroon po kaming 1-Click OnePass SSO na sumusunod sa RFC 6749 at RFC 7636 PKCE S256 standard! 
Pag-click po nito, awtomatiko itong magdidirekta sa OnePass authorization server. Pagka-authorize po ng student, babalik ito sa aming app kung saan kukunin ng Laravel ang verified student claims, at lilitaw agad ang verified identity ng student sa header profile dropdown kasama ang kanyang kurso at section! 
Pansinin din po sa loob ng Profile Dropdown: dito po namin inilagay ang 'Admin Management Console' na may Role-Based Access Control (RBAC). Kung ang account tulad ng `ics@npc.edu.ph` ay awtorisadong Administrator sa ating database, 1-click lang po mula sa dropdown ay makakapasok na siya sa buong Admin Management Dashboard nang malinis at walang gulo sa header!"

HAKBANG 2 (Catalog, Size Selection & Cart - Member 1):
"Makikita po ang aming dynamic catalog na pwedeng i-filter ayon sa Department o P.E. uniform. Kapag pumili po ang student ng item, halimbawa ang 'ICS Official Polo Shirt', makikita ang atomic stock counter bawat sukat: XS hanggang 2XL. Pipili po tayo ng Size Medium at i-click ang 'Add to Cart'.
Bubukas po ang aming responsive Cart Drawer na binuo gamit ang Tailwind CSS at LocalStorage. I-click po natin ang 'Proceed to Checkout'. Dito po awtomatikong naka-populate ang kanyang verified student information mula sa OnePass session! Pipiliin po natin ang 'GCash Online', ilalagay ang GCash Reference Number, at mag-a-upload ng sample receipt image. Pag-click po ng 'Submit Reservation'..."

HAKBANG 3 (Instant Realtime Admin Sync - Member 2):
"Pansinin po ninyo sa kanang window na Admin Portal: Nang hindi po nire-refresh ang page, lumitaw agad ang bagong reservation sa aming Reservation Queue sa loob lamang ng 3 segundo dahil sa aming Background Real-Time Polling Engine! Na-bawas na rin po agad sa database ang stock ng Medium polo upang hindi ito ma-order ng iba."

HAKBANG 4 (Filing a Ticket & Conflict Lock Demonstration - Member 2):
"Ngayon po, ipapakita namin ang isa sa aming pinakamalaking safety features: ang 'Conflict Lock Engine'. Halimbawa, nagkamali ang student at nais niyang magpalit ng size o mag-cancel. Magbubukas po ang student ng Helpdesk Ticket gamit ang kanyang Reference Code. 
Pagkapasa po ng ticket... Tingnan ninyo po ang Admin Queue! Awtomatikong nag-flash ang babalang:
'⚠️ ON HOLD: Active Support Ticket'
Naka-disable po ngayon ang 'Mark Ready for Pickup' at 'Mark Claimed' buttons. Hindi po papayagan ng aming Laravel backend ang admin na i-release ang damit habang may nakabinbing reklamo ang estudyante!"

HAKBANG 5 (Turn-Taking Anti-Spam Chat - Member 2):
"Sa Helpdesk Chat naman po, ipinatupad namin ang 'Turn-Taking Anti-Spam Policy'. Kapag nagpadala po ang student ng message, naka-lock agad ang kanyang input box at may warning na 'Please wait for an admin to reply before sending another message'. Hindi po siya makakapag-spam ng messages.
Ngayon, sasagot po ang admin mula sa Admin Portal: 'Hello, na-receive po namin ang request ninyo.' 
Pagka-send po ng admin, kusa pong mag-a-unlock ang chat input ng student! Maayos at regulated po ang daloy ng komunikasyon."

HAKBANG 6 (Ticket Resolution & Stock Restocking - Member 2):
"Kung cancellation po ang napagkasunduan, iki-click lamang ng admin ang 'Cancel Reservation & Restock'. Awtomatikong ibinabalik ng server ang stock sa produkto at minamarkahang 'Resolved' ang tiket."

HAKBANG 7 (Finished Reservation & Ticket Deletion Governance - Member 1):
"Para naman po sa logistics hygiene at safety, habang Open ang ticket, bawal itong burahin. Ngunit ngayong Resolved na, lumilitaw na ang 'Delete Ticket' button kung saan gagamitin ng MySQL ang `ON DELETE CASCADE` para linisin ang messages.
Gayundin sa Reservation Queue: kapag natapos na ang order (Claimed o Cancelled), lumalabas ang pulang 'Delete Order' button upang tuluyang linisin ang natapos nang transaksyon sa database nang hindi nagre-redirect sa ibang tab."

[YUGTO 3: TECHNICAL DEEP DIVE (BACKEND, DATABASE, SYSTEM SUPPORT, & DOCS)]
--------------------------------------------------------------------------------

MEMBER 2 (Backend Logic & Security - Task 1 & Task 4A):
"Tungkol naman po sa aming Server-Side Backend Architecture:
1. Ang aming backend controllers (`MerchController.php` at `OAuthController.php`) ay naglalaman ng 25 modular public routes at API endpoints na sumasaklaw sa kumpletong CRUD, state transitions, authentication, at audit logging.
2. Sa aspeto ng Security Compliance, 100% po ng aming mutating routes ay protektado ng CSRF meta token validation.
3. Para maiwasan ang SQL Injection, wala po kaming kahit isang raw SQL query string; lahat po ay dumadaan sa Eloquent ORM na may PDO parameter binding.
4. Ang bawat controller method ay may komprehensibong HTTP request validation upang masala ang maling input bago pa man makarating sa database.
5. Ipinatupad din po namin ang OnePass OAuth 2.0 / OIDC architecture sa `OAuthController.php` gamit ang RFC 7636 PKCE S256 at resilient server-to-server token exchange sa `/api/oauth/token`."

(Ipapasa ang mic kay Member 3)

MEMBER 3 (Database Architecture & Dev Setup - Task 3 & Task 4B):
"Para naman po sa aming Database Layer at System Support:
1. Ang aming database ay tumatakbo sa MySQL 8.0 gamit ang InnoDB storage engine upang magarantiyahan ang full ACID compliance (Atomicity, Consistency, Isolation, Durability).
2. Mayroon po kaming pitong (7) tables kabilang ang `students` identity table, na may strict Foreign Key constraints at B-Tree indexes sa `student_id`, `reservation_ref`, at `status`.
3. Naka-integrate din po ang aming system sa Supabase Cloud (`oyzvcqaytavbfwdrgili.supabase.co`) para sa real-time cloud auth synchronization.
4. Ginamit po namin ang 'JSON Snapshot Pattern' sa mga order items at product sizes upang maiwasan ang historical price corruption at mapabilis ang read latency.
5. Sa aspeto ng Dev Setup at Git Workflow, ang aming credentials ay nakahiwalay sa `.env` file, may malinis kaming `.gitignore`, at binuo ang database gamit ang reproducible Laravel Migrations at Seeders."

(Ipapasa ang mic pabalik kay Member 1)
