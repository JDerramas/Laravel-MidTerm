II. DATABASE JOURNEY: PANO MO NILIPAT SA TIDB SERVERLESS CLOUD
================================================================================

1. BAKIT KINAILANGANG ILIPAT MULA XAMPP PATUNGO SA CLOUD DATABASE?
   - Noong una, tumatakbo ang database sa local XAMPP MySQL (`localhost:3306`).
   - Problema: Noong i-de-deploy na natin ang Laravel application sa internet sa Render.com,
     hindi kayang ma-access ng cloud server sa Render ang `localhost` ng iyong laptop
     nang walang komplikadong port-forwarding o pag-iiwan ng laptop na nakabukas 24/7.
   - Solusyon: Kinailangan natin ng isang totoong cloud-hosted MySQL database.
     Pinili natin ang **TiDB Serverless Cloud** dahil:
     * 100% MySQL 8.0 compatible (gumagana ang lahat ng Laravel migrations at queries).
     * Naka-host sa **AWS Singapore (`ap-southeast-1`)** kaya napakababa ng network latency (mabilis).
     * Serverless at may auto-scaling, libre, at may mataas na uptime availability.

2. HAKBANG-HAKBANG NA PAGLIPAT SA TIDB CLOUD:
   • Hakbang 1 (Paggawa ng TiDB Cluster):
     - Nag-register tayo sa TiDB Cloud console (tidbcloud.com).
     - Gumawa tayo ng bagong Serverless Cluster sa region na AWS Singapore (ap-southeast-1).
     - Kinuha natin ang mga bagong connection credentials:
       * Host: `gateway01.ap-southeast-1.prod.aws.tidbcloud.com`
       * Port: `4000` (HINDI default 3306! Ang TiDB Cloud ay gumagamit ng Port 4000).
       * Database: `my_laravel`
       * Username at generated secure Password.

   • Hakbang 2 (Export ng Local Database Schema & Data):
     - In-export natin ang kumpletong schema at records mula sa local XAMPP MySQL
       patungo sa `database/my_laravel.sql`.
     - Naglalaman ito ng 7 core tables: `products`, `reservations`, `students`,
       `system_users`, `support_tickets`, `support_ticket_messages`, at `activity_logs`.

   • Hakbang 3 (Configuration ng SSL CA sa Laravel `config/database.php`):
     - Dahil ang TiDB Cloud ay mahigpit na nag-re-require ng TLS/SSL encrypted connection,
       nag-error noong una ang connection kapag walang SSL options.
     - In-update natin ang `config/database.php` sa ilalim ng `mysql` connection:
       ```php
       'options' => extension_loaded('pdo_mysql') ? array_filter([
           PDO::MYSQL_ATTR_SSL_CA => env('MYSQL_ATTR_SSL_CA', '/etc/ssl/certs/ca-certificates.crt'),
           PDO::MYSQL_ATTR_SSL_VERIFY_SERVER_CERT => false,
       ]) : [],
       ```
     - Sa Windows local machine, gumagana ito sa curl-ca-bundle; sa Linux Docker container naman
       sa Render, ginagamit nito ang standard `/etc/ssl/certs/ca-certificates.crt`.

   • Hakbang 4 (Pag-import ng Tables at Testing):
     - Gamit ang remote connection script, matagumpay nating na-execute ang SQL dump
       sa TiDB Cloud server sa Singapore.
     - Na-verify natin gamit ang PHP command-line tests na lahat ng 16 tables/records
       ay 100% intact, readable, at writable.

3. ANG ERROR NA HINARAP SA DATABASE AT PAANO NATIN NAAYOS:
   • Error: `SQLSTATE[23000]: Integrity constraint violation: 1062 Duplicate entry`
   • Ano ang nangyari?
     - Sa `students` table, may existing record na para sa email mo
       (`jderramas251505@navotaspolytechniccollege.edu.ph`) pero ang dating student_id ay `251505`.
     - Nang mag-login ka gamit ang OnePass OAuth, nagpadala ang OnePass ng internal ID na `28`.
     - Ang lumang backend code ay nag-attempt mag-INSERT gamit ang ID 28 at ang existing email mo.
     - Dahil may `UNIQUE` key constraint ang `email`, nag-crash ang database!
   • Paano mo naayos?
     - Una, in-update natin ang record mo sa TiDB Cloud database na maging `student_id = 28`
       para mag-match sa OnePass token at sa lahat ng naunang reservations mo.
     - Pangalawa, sa `OAuthController.php`, binago natin ang query:
       Gumawa tayo ng **Smart Lookup**:
       ```php
       $existingStudent = Student::where('email', $email)
           ->orWhere('student_id', $studentId)
           ->first();
       ```
       Kung may mahanap na student sa email O student ID, i-uupdate na lang ang profile
       sa halip na mag-insert ng panibago.
     - Binalot din natin ito sa defensive `try / catch` block upang garantisadong
       hindi magka-crash ang screen ng estudyante kailanman.

III. SYSTEM SUPPORT & DEVOPS: RENDER CLOUD, DOCKER, AT UPTIMEROBOT
================================================================================

1. LIVE CLOUD HOSTING SA RENDER.COM GAMIT ANG DOCKER:
   - Sa halip na iasa sa localhost o sa mabagal na cloud tunnels, nag-deploy tayo ng
     production web service sa **Render.com**.
   - Gumawa tayo ng custom multi-stage `Dockerfile`:
     * Base Image: `php:8.2-apache` (o PHP 8.2 FPM + Nginx).
     * Installed Extensions: `pdo_mysql`, `bcmath`, `gd`, `zip`, at `mbstring`.
     * Apache Rewrite: In-enable ang `a2enmod rewrite` para sa malinis na Laravel routes.
     * Web Root Isolation: Ini-set ang `APACHE_DOCUMENT_ROOT` sa `/var/www/html/public`.
       Bakit? Para hindi ma-expose sa internet ang sensitibong `.env` file at core code!
     * Optimization: `composer install --no-dev --optimize-autoloader`.

2. ENVIRONMENT CONFIGURATION SA RENDER:
   - Inilagay natin ang mga production environment variables sa Render Dashboard:
     * `APP_NAME="ICS Apparel & Merchandise Reservation System"`
     * `APP_ENV=production`
     * `APP_DEBUG=false` (para walang leaks ng sensitive stack traces)
     * `APP_URL=https://laravel-midterm-8n2y.onrender.com`
     * `APP_KEY=base64:...` (sariwang 32-character encryption key)
     * `DB_CONNECTION=mysql`
     * `DB_HOST=gateway01.ap-southeast-1.prod.aws.tidbcloud.com`
     * `DB_PORT=4000`
     * `DB_DATABASE=my_laravel`
     * `DB_USERNAME` at `DB_PASSWORD` ng TiDB Cloud
     * OnePass OAuth credentials: Client ID at Client Secret

3. ANG ERROR SA RENDER DEPLOYMENT AT PAANO NAAYOS:
   • Incident 1: 500 Server Error sa unang deploy.
     - Sanhi: Default DocumentRoot ng Apache ay nasa `/var/www/html/` imbes na `/var/www/html/public/`,
       at kulang ng `APP_KEY`.
     - Fix: Inayos ang Dockerfile Apache configuration at nag-set ng `APP_KEY` sa Render.
   • Incident 2: OnePass OAuth "400 Bad Request" error.
     - Sanhi: Ang naka-whitelist na Redirect URI sa OnePass Developer Portal ay
       `https://app.npc.edu.ph/auth/callback` imbes na ang live Render URL natin.
     - Fix: In-update natin ang Redirect URIs sa OnePass Client settings para isama ang:
       `https://laravel-midterm-8n2y.onrender.com/oauth/callback`
       at in-align ang authorized scopes sa `OAuthController.php`.

4. 24/7 AVAILABILITY VIA UPTIMEROBOT KEEP-ALIVE:
   - Problema sa Render Free Tier: Kapag walang bumibisita sa website sa loob ng 15 minutes,
     kusa itong natutulog (sleep mode / spin down). Pag may nag-access ulit, may 30-50 seconds
     na cold-start delay bago magbukas.
   - Solusyon: Nag-setup tayo ng automated monitor sa **UptimeRobot**.
     Bawat 5 minuto, nagpapadala ito ng automated lightweight HTTP GET request sa
     `https://laravel-midterm-8n2y.onrender.com`.
   - Resulta: Laging gising at mainit ang server, kaya instant 200 OK agad kapag
     binuksan ng panel o ng prof sa mismong araw ng defense!

IV. SUPPORT SYSTEM & REAL-TIME NOTIFICATION ENGINE
================================================================================

1. TWO-WAY CUSTOMER HELPDESK & TURN-TAKING ANTI-SPAM:
   - Ang mga estudyante ay pwedeng magbukas ng Support Ticket (`TCK-2026-XXXX`).
   - May live two-way chat window sa pagitan ng Student at Admin.
   - May **Turn-Taking Anti-Spam Guard**: Bawal mag-flood ng messages ang student
     hangga't hindi pa sumasagot ang admin, at vice versa.
   - May **Conflict Lock Engine (`⚠️ ON HOLD`)**: Habang may bukas na reklamo ang student,
     naka-disable sa Admin Queue ang button na mag-mark ng "Claimed" o "Ready for Pickup".

2. REAL-TIME ACTIVITY LOGS & FLOATING TOAST NOTIFICATIONS:
   - Lahat ng aksyon sa system ay nire-record sa `activity_logs` table:
     * LOGIN: Estudyante o Admin na nag-sign in.
     * LOGOUT: Session sign-out.
     * CREATE / UPDATE: Bagong reservations, stock adjustment, item update.
     * DELETE: Pag-delete ng item o pag-clear ng audit logs.
   - Sa backend, sa `MerchController::getRealtimeSync`, kapag `scope === 'admin'`,
     ibinabalik ang pinakabagong `activity_logs` sa 2-second background sync payload.
   - Sa frontend `admin.blade.php`:
     * Sinusubaybayan ang `lastSeenActivityLogId`.
     * Kapag may pumasok na mas bagong log ID, automatic na nagpa-pop up ang
       Floating Toast Alert (Green para sa Login/New, Amber para sa Logout, Red sa Delete).
     * Tumutunog ang Web Audio API synth chime sound.
     * Dynamic na inire-render ang table sa Module 6 nang walang manual page refresh.
   - Naglagay din tayo ng dedicated Admin Sign Out button sa header na nagte-trigger
     ng official `LOGOUT` audit log.
